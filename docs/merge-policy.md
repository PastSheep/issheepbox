# 合并与审查策略（Merge Policy）

本文档定义合并流程与 main 分支的保护规则。文档同时适用于主 agent（合并者）与其按需派发的**合并子 agent**。

## 0. 执行者

- **合并流程由合并子 agent 执行**：需求方将执行 agent 的完成汇报（分支名、改动摘要、涉及文件）转交主 agent 后，主 agent 派发合并子 agent，并附上汇报信息与本文档路径。
- 合并子 agent 在 `workspaces/merger` 工作区操作，代表合并者执行第 2~5 节全部规则。
- 合并子 agent 完成后向主 agent 汇报：审查结论、合并提交号、是否打回；主 agent 转达需求方，不重复检查。
- **主 agent 不亲自逐文件审查**，以精简上下文；仅在合并子 agent 报告异常（如冲突需需求方裁决）时介入沟通。

## 1. main 保护规则

1. **main 唯一写者是合并者（含其派发的合并子 agent）**。任何其他 agent、外部进程不得直接推送 main。
2. main 必须始终处于**可构建、可运行**状态；无法通过检查的改动不得进入 main。
3. 合并采用 **merge commit**（`--no-ff`），保留分支历史，便于回溯每个任务由谁完成。
4. 合并完成后立即删除已合并的分支（远端），保持分支列表干净。

## 2. 审查清单

合并任何分支前，执行合并的 agent（合并子 agent）逐项检查：

- [ ] 分支基于最新的 main（不是过期状态）
- [ ] 提交信息符合 `docs/conventions.md`，正文写明了「改了什么 / 为什么」
- [ ] 改动范围与任务描述一致，没有夹带无关修改
- [ ] 代码可构建、测试通过（运行构建/测试命令验证）
- [ ] 没有提交密钥、凭据、本机专属路径
- [ ] 没有把不应入库的产物（缓存、二进制、依赖目录）提交进来

任何一项不满足：打回分支，说明原因，由对应 agent 修复后重新推送。

## 3. 合并执行步骤

```
1. git fetch origin                       # 拉取全部 agent 分支
2. git checkout main && git pull          # 确保 main 最新
3. 逐个分支：
   a. git merge --no-ff <agent-name>/<任务标识>
   b. 若有冲突 → 按第 4 节解决
   c. 运行构建/测试验证
   d. git push origin main
   e. git push origin --delete <agent-name>/<任务标识>   # 清理已合并分支
4. 更新 docs/TASKS.md：任务状态 → 已完成
5. 通知各 agent：main 已更新，请 pull 同步
```

## 4. 冲突解决原则

多 agent 并行开发，冲突是预期内的事件，解决顺序：

1. 先读冲突双方提交信息的**正文**，理解各自「为什么改」。
2. 目标一致（如两个都修同一 bug）→ 取更完整/更新的实现。
3. 目标冲突（如对同一接口的不同设计）→ 不擅自裁决，列出差异与影响，向需求方确认后合并。
4. 涉及热点文件（高频冲突）→ 在文档中登记，建议后续 agent 错峰修改。
5. 冲突解决后，合并信息中必须注明「如何解决冲突、为什么保留某一边」，保证可追溯。

## 5. 打回与归档

- 审查不通过的分支：合并子 agent 留言说明问题，分支保留在远端等 agent 修复重推，并向主 agent 报告打回原因。
- 任务取消的分支：合并子 agent 删除远端分支；若含未合并价值代码，先在 `docs/TASKS.md` 记录要点再删。
- 长期不活跃 agent 的分支：归档（打 tag `archive/<agent-name>/<date>`）后删除，避免堆积。
